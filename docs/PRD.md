# 简单版 PRD：仿千千静听跨平台音乐播放器

> 文档类型：简单版 PRD（默认结构） ｜ 面向对象：架构师 / 开发 ｜ 作者：产品经理 许清楚（Xu）

## 0. 原创产品名建议

本项目为「仿」千千静听，仅复刻交互范式与功能集，**不内置其品牌名、Logo、专有皮肤素材、专有音频解码库**。需使用原创品牌与自有素材以规避侵权。

- **主推名称：「聆风」（Lingfeng / 拼音：Língfēng）**
  - 意象：「聆听风声与旋律」，中性、无既有品牌冲突，可注册。
  - 英文标识建议：`Lingfeng Player` 或缩写 `LFPlayer`。
- **备选名称**：弦音（Xianyin）｜听潮（Tingchao）｜乐聆（Leling）｜韶律（Shaolü）。
- **占位说明**：下文统一以「聆风」代指本产品；Logo、皮肤素材、解码能力均由团队原创/开源方案提供。

---

## 1. 产品目标

「聆风」是一款基于 Rust + iced（MVU 架构）开发的跨平台桌面音乐播放器，面向 Windows / macOS / Linux 用户，复刻千千静听经典的交互范式与功能集（播放与播放列表管理、同步滚动 LRC 歌词与迷你歌词、多频段均衡器/DSP 音效、可换肤 UI 与迷你模式及系统托盘控制、分段 LED 风格频谱可视化），以低资源占用、原生跨平台一致体验和轻量可定制的怀旧视觉为差异化，为追求经典操作手感与音质调节能力的本地音乐听众提供一款现代、开源、无侵权的播放工具。

## 5. 技术约束

- **语言与框架**：Rust + **iced**（采用其 MVU 架构：State → View → Message → Update）。UI 状态集中管理，频谱/歌词/播放为独立订阅（Subscription）。
- **目标平台**：Windows / macOS / Linux，三端二进制一致构建；注意平台托盘 API 与窗口置顶/半透明差异（macOS 需 `NSWindow` 级别处理）。
- **音频后端选型（建议）**：
  - 解码：**Symphonia**（纯 Rust，支持 MP3/FLAC/WAV/OGG 等多格式，无系统依赖）。
  - 输出：**cpal**（跨平台音频输出）+ **rodio** 可选封装；或直接 rodio 解码+播放。
  - 推荐组合：**Symphonia 解码 → cpal 输出**，并在解码后的 PCM 流上挂载均衡器/DSP 与频谱分析节点。
- **LRC 解析**：自研轻量解析器，处理 `[mm:ss.xx]` 多时间戳、多行合并、编码（UTF-8/GBK 回退）。
- **频谱数据来源**：对输出前 PCM（如 1024/2048 点窗口）做 **FFT**（如 `rustfft`），映射为 N 个频段能量 → 分段 LED 渲染；采样与渲染经 Subscription 异步推送，避免阻塞 UI。
- **DSP/均衡器**：在 PCM 处理链中插入多频段 IIR（Biquad）滤波实现均衡；主增益置于链首/链尾。
- **持久化**：播放列表、皮肤选择、均衡器预设、窗口状态存本地（如 `dirs` 配置目录下的 JSON/SQLite）。
- **侵权规避**：不使用千千静听名称/Logo/专有皮肤/专有解码库；全部素材原创或采用开源/自由许可资源。

## 6. 待确认问题

1. **在线歌词接口**：是否首版接入在线歌词搜索？若接入，采用自建占位接口还是第三方（需评估合规/费用/隐私）？默认建议首版仅做本地匹配 + 接口占位（REQ-205 为 P1）。
2. **皮肤格式与制作工具**：皮肤采用纯 JSON 还是配套可视化编辑器？是否需要开放社区皮肤生态（影响 REQ-405/407 范围）。
3. **音频后端最终选型**：Symphonia+cpal 组合 vs. rodio 一体化，需架构师结合 DSP 链路灵活度确认（P0 功能依赖此决策）。
4. **频谱 FFT 参数与性能预算**：频段数（如 16/32 段）、刷新率（建议 30–60fps）、是否需 GPU 加速渲染（影响三端性能）。
5. **全局热键与平台权限**：macOS 全局热键/无障碍权限、Windows 托盘行为差异是否需在首版全部支持，还是先保证主窗口内快捷键。

### INC-1（P0）：主窗口改为千千静听经典「竖窄窗口」

#### 1.1 问题陈述

v0.1 主窗口实现为 **960×640 横宽三栏**（列表左 + 歌词右 + 频谱下 + 均衡器底），与千千静听经典「**竖窄单列**」形态不符；且均衡器位于底部、被窗口高度**截断**（10 段仅显示到 2kHz），P0 控件不可用。**这是形态级需求偏差，非样式微调。**

#### 1.2 默认窗口尺寸与比例

| 项 | 取值 | 说明 |
|----|------|------|
| 默认宽 | **340 px**（可 300–400） | 竖窄基准 |
| 默认高 | **640 px**（可 600–680） | 与宽比约 **1.88 : 1** |
| **高:宽 比例下限** | **≥ 1.6 : 1** | 硬性验收线（640/340≈1.88 ✓） |
| min_size | **320 × 520** | 低于此值 P0 控件无法完整排布 |
| 是否允许拉宽 | **允许**，但默认启动必须竖窄；拉宽不得改变单列纵向结构 | 参考千千静听可横向拉伸列表列宽 |
| 尺寸持久化 | **持久化**（写入 `Settings`，重启恢复），见 REQ-409 | 首次运行用默认 340×640 |

> 关键约束：**默认启动即竖窄窗口**是验收硬指标；用户手动拉伸后保持其尺寸，但不提供"默认横宽"。

```
│ │   （竖向滚动条）                ││
│ └───────────────────────────────┘│
├───────────────────────────────┤
│  ▼ 均衡器（折叠头，点击展开）      │ ⑦ 均衡器：可折叠面板（默认收起）
│  展开后 10 段全部可见（内部滚动）   │    31Hz…16kHz 十段不截断
└───────────────────────────────┘
```

**分区职责表**

| # | 分区 | 高度/占比 | 控件 | 备注 |
|---|------|-----------|------|------|
| ① | 标题栏 | ~32px 固定 | 产品名「聆风」+ 皮肤选择 + 迷你模式 + 迷你歌词 + 窗口控制 | 迷你歌词按钮为入口 |
| ② | 当前曲目信息 | ~28px 固定 | 标题 / 艺术家（**单行省略号截断**） | 过长以 `…` 收尾 |
| ③ | LED 分段频谱 | **70–90px** 固定 | 分段 LED 竖直条（实时） | 暂停/静音归零 |
| ④ | 进度条 + 时间 | ~28px 固定 | 拖拽 seek + `当前/总` 时间 | REQ-104 |
| ⑤ | 控制行 | ~36px 固定 | ⏮ ⏯ ⏭ + 音量 + 静音 + **循环模式**（单曲/列表/随机/顺序） | REQ-103/105 |
| ⑥ | **播放列表** | **剩余自适应（默认 ≥260px），可滚动** | 列表项（标题+时长）、添加/清空/排序 | **「列表即主体」**，竖向第一大区 |
| ⑦ | 均衡器 | **可折叠**（收起 ~24px 头 / 展开 ~150px，内部滚动） | 10 段滑块（31Hz–16kHz）+ 预设 | **确保 10 段可达不截断** |

#### 1.4 均衡器防截断方案（三选一，产品推荐 A）

| 方案 | 描述 | 优点 | 缺点 | 倾向 |
|------|------|------|------|------|
| **A. 可折叠面板（推荐）** | 标题栏下方/列表下方「▼ 均衡器」折叠头，点击展开；展开时**面板内部竖向滚动**，10 段全部可达 | 不占常态空间，符合竖窄形态；实现简单 | 展开后压缩列表可视高度 | **✅ 默认采用** |
| B. 弹出面板 | 点按钮弹出独立 EQ 窗口/浮层 | 常态最干净 | 多窗管理成本、与"单窗经典"略有出入 | 备选 |
| C. 内部横向滚动 | EQ 固定高度，10 段横向滚动查看 | 保持纵向结构 | 拖动手感差、隐藏段不易发现 | 不推荐 |

> 无论 A/B/C，**验收底线一致：10 段（31Hz–16kHz）全部可见可调，无任何波段被窗口高度截断。**

#### 1.5 歌词区与频谱在竖窄窗口中的归属（明确取舍）

| 内容 | 归属决策 | 理由 |
|------|----------|------|
| **同步滚动 LRC 歌词** | **主窗不再默认占用独立右栏**。主窗通过**「列表 / 歌词」标签切换**（Tab）复用 ⑥ 区域显示歌词；同时保留**迷你歌词窗口**（REQ-204）承担"边工作边看词" | 竖窄窗口放不下"列表+歌词"双栏；标签切换兼顾两者 |
| **迷你歌词** | 独立常驻小窗（永不变更），为主窗之外的首选看词方式 | 沿用 REQ-204 |
| **LED 频谱** | **保留在主窗 ③ 区**（窄条 70–90px，与窗口等宽） | 千千静听经典元素，竖窄下仍成立；迷你模式可简化（REQ-505） |

> 取舍结论：**主窗 = 单列纵向（列表为主，歌词按 Tab 切换）；看词主推迷你歌词窗。** 频谱保留主窗窄条。

### INC-2（P0）：中文 / CJK 全 UI 可读性（消除 tofu 乱码）

#### 2.1 问题陈述

v0.1 所有中文字符渲染为**空白方块（tofu）**，拉丁字符正常；日志 `failed to load font 'GB18030Bitmap'`。即 **UI 未加载任何可用的 CJK 字体**，属 v0.1 **验收硬伤**。原 REQ-406 仅 P1 且未给字体加载方案，**档位与方案双缺失**。

#### 2.2 需求编号（新增 / 修订）

| 编号 | 描述 | 优先级 | 验收标准 |
|------|------|--------|----------|
| **REQ-406**（修订） | 高分屏/缩放适配；**UI 必须加载可用 CJK 字体**，三平台一致 | **P0**（原 P1） | 三平台清晰度一致；**无 tofu / 乱码** |
| **REQ-408**（新增） | **CJK 字体加载与覆盖**：主窗口 + 迷你模式 + 迷你歌词 + 托盘菜单 + 所有对话框（如"打开文件"标题、错误提示、皮肤名）中文均正常渲染 | **P0** | 全 UI 中文正常显示，无方块；三平台一致；全新环境启动即生效 |

#### 2.3 字体方案（业务要求，不限定实现）

> 目标：**三端一致 + 授权干净 + 全新环境零配置即可读**。

| 方案 | 描述 | 优点 | 缺点/风险 | 产品倾向 |
|------|------|------|-----------|----------|
| **A. 随包分发开源 CJK 字体（推荐）** | 内嵌一款开源黑体（**Noto Sans SC / 思源黑体 Source Han Sans SC / 霞鹜文楷 LXGW WenKai** 等，注意各自授权：OFL/ SIL） | **三端渲染完全一致**；离线可用；不依赖系统字体 | 安装包体积增大（全量思源黑体 ~16MB+，可选**子集化/精简字重**控制） | **✅ 首选** |
| B. 系统字体回退 | macOS `PingFang SC` / Windows `Microsoft YaHei` / Linux `Noto Sans CJK SC`，按平台探测 | 零体积、清晰 | 三端字形不一致；Linux 精简发行版可能缺字体 → 仍 tofu | 备选（作为 A 的兜底） |
| **A+B 混合（最终建议）** | **随包内嵌** CJK 字体为主 + 启动时**系统字体探测兜底** | 一致性与健壮性兼得 | 实现略增 | **✅ 推荐落地组合** |

**业务硬要求（写给架构师/工程师）**：
1. 应用启动时**必须显式加载**随包 CJK 字体（不得再依赖 `'GB18030Bitmap'` 这类不可用字体名）。
2. 字体加载需覆盖 **iced 默认字体族与所有自定义控件（canvas LED、进度条等）的中文文本**。
3. 至少保证：常规字重 + 一个粗体（如需强调标题）；含**常用汉字 + 标点 + 全角符号**。
4. 若字体内嵌，**须注明授权并随包附 LICENSE**（规避侵权，延续 §0 合规原则）。
5. 三平台（Windows / macOS / Linux）构建产物**行为一致**，不得只在开发机可读。

### 9. 待确认问题（3–5 条）

1. **默认窗口比例是否锁定？** 是否接受"默认 340×640、允许用户拉宽但保持单列"？还是必须**锁定竖窄比例、禁止横向拉宽**（更贴近原版但牺牲灵活性）？
2. **均衡器折叠方式偏好？** 采用 §1.4 推荐 **A. 可折叠面板（默认收起，展开内部滚动）**，还是希望 **B. 独立弹出 EQ 窗口**？
3. **字体策略：随包分发 vs 系统回退？** 是否接受为一致性**增大安装包体积**（内嵌思源黑体/Noto Sans SC）？还是优先系统字体回退（体积小但 Linux 存风险）？产品建议 A+B 混合。
4. **主窗是否需要「列表 / 歌词」标签切换？** 若竖窄窗口只保留列表、歌词完全交给迷你歌词窗，是否可接受？（影响 §1.5 取舍）
5. **迷你歌词窗是否默认随主窗启动？** 主窗去掉默认歌词栏后，是否改为**默认打开迷你歌词窗**以保证看词体验不降级？
